Configuration Layer

Configuration — The Factory's Blueprint

.bruin.yml — The Address Book

🏭 Analogy

This file is the factory's address book — it tells Bruin where all the external services and databases live, so every asset knows how to connect.

📄 .bruin.yml YAML 
default_environment: default        # Which environment to use by default
environments:
    default:
        connections:
            duckdb:                       # Connection type
                - name: duckdb-default        # A reusable name for this connection
                  path: ./zoomcamp/pipeline/duckdb.db  # Where the database file lives

What this does: Defines one environment called default with a single DuckDB connection. The database file lives at ./zoomcamp/pipeline/duckdb.db. Every asset that references duckdb-default will read/write to this file.

pipeline.yml — The Production Schedule

🏭 Analogy

This is the production schedule pinned to the factory wall — it says when the assembly line runs, what date range to process, and what kind of products (taxi types) to handle.

📄 pipeline.yml YAML 
name: zoomcamp                  # Pipeline identifier
schedule: monthly                # Runs once per month
start_date: "2022-01-01"         # The beginning of time for this pipeline

default_connections:
  duckdb: duckdb-default          # All DuckDB assets use this connection

variables:
  taxi_types:
    type: array
    items:
      type: string
    default: ["yellow", "green"]   # Process both yellow and green taxis

Key concepts explained:

schedule: monthly
Bruin runs this pipeline once per month. Each run processes one month of data.
start_date
The earliest date this pipeline cares about. Bruin will never try to process data before Jan 1, 2022.
default_connections
Instead of repeating the connection in every asset, set it once here. All DuckDB assets auto-connect to duckdb-default.
variables
Custom parameters passed to assets. Here, taxi_types tells the Python ingestion script to fetch both yellow and green taxi data.

What's a "Seed"?

A seed is Bruin's way of loading a small, static CSV file directly into a database table. Unlike dynamic assets that compute data, seeds just copy rows as-is. They're perfect for lookup tables, reference data, or any small dataset that rarely changes.

Quality Checks

Even for this tiny table, Bruin verifies:

not_null
Every row must have a value — no blanks allowed.
unique
No two rows can share the same payment_type_id.
primary_key
Marks payment_type_id as the row identifier — combining not_null + unique.

Let's walk through the code piece by piece:

1. The Bruin Header (Asset Metadata)

📄 trips.py — header PYTHON 
"""@bruin

name: ingestion.trips       # Table will be: ingestion.trips
type: python                 # This asset runs Python code
image: python:3.11           # Docker image to run in
connection: duckdb-default   # Which DB connection to write to

materialization:
  type: table                # Create a table (not a view)
  strategy: append            # ADD new rows, never delete old ones

@bruin"""

The """@bruin ... @bruin""" block is a special docstring that Bruin reads. It's how you declare metadata in Python assets. Key detail: strategy: append means each run adds rows to the table — it never deletes previous data. This is safe for historical data that shouldn't change.

2. The materialize() Function

📄 trips.py — materialize() PYTHON 
def materialize():
    # Bruin injects these environment variables:
    start_date = os.environ.get("BRUIN_START_DATE", "2022-01-01")
    end_date = os.environ.get("BRUIN_END_DATE", "2022-02-01")
    bruin_vars = json.loads(os.environ.get("BRUIN_VARS", "{}"))
    taxi_types = bruin_vars.get("taxi_types", ["yellow"])

    start = datetime.strptime(start_date, "%Y-%m-%d")
    end = datetime.strptime(end_date, "%Y-%m-%d")

    all_frames = []
    current = start
    while current < end:
        year_month = current.strftime("%Y-%m")
        for taxi_type in taxi_types:
            filename = f"{taxi_type}_tripdata_{year_month}.parquet"
            url = f"{BASE_URL}{filename}"
            print(f"Fetching {url}")
            try:
                df = pd.read_parquet(url)     # Download Parquet directly
                df["taxi_type"] = taxi_type   # Tag the source
                df["extracted_at"] = datetime.utcnow()
                all_frames.append(df)
            except Exception as e:
                print(f"  -> Failed: {e}")
        current += relativedelta(months=1)

    if not all_frames:
        return pd.DataFrame()

    result = pd.concat(all_frames, ignore_index=True)
    return result

Key Concepts Explained

BRUIN_START_DATE / END_DATE
Bruin injects these as environment variables. For a monthly schedule, each run gets one month (e.g., 2022-01-01 to 2022-02-01).
BRUIN_VARS
A JSON string containing the pipeline variables. Here it carries taxi_types: ["yellow", "green"].
Parquet
A columnar file format that's compressed and fast to read. Much better than CSV for large datasets. Pandas can read them directly from a URL.
materialize()
The magic function name. Bruin calls this and takes the returned DataFrame, then writes it to the database table defined in the header.
strategy: append
New rows are always added. Old rows are never touched. If you re-run a month, you get duplicate data — by design, the staging layer handles deduplication.
extracted_at
A timestamp column added by the code to track when each batch was fetched. Used later for deduplication (keep the newest extraction).

Staging — Quality Control & Sorting

staging/trips.sql — The Cleaning Station

🏭 Analogy

This is the quality control and sorting station. Raw materials arrive messy — duplicates, inconsistent column names, cryptic codes. This station deduplicates, standardizes, and enriches the data before it moves to the next phase.

Asset Header

📄 trips.sql — header SQL 
name: staging.trips
type: duckdb.sql

depends:                          # Must run AFTER these assets
  - ingestion.trips
  - ingestion.payment_lookup

materialization:
  type: table
  strategy: time_interval          # Only process new time windows
  incremental_key: pickup_datetime # The column that defines "time"
  time_granularity: timestamp
strategy: time_interval
Instead of reprocessing ALL data every run, only process the new time window. For a monthly schedule, each run only handles one month of new data. This is incremental processing.
incremental_key
The column Bruin uses to know which rows are "new." It filters: WHERE pickup_datetime >= start AND pickup_datetime < end.
depends
Declares that this asset cannot run until both ingestion.trips and ingestion.payment_lookup have finished. This is how Bruin builds the execution order (lineage/DAG).

The SQL — Step by Step

Step 1: CTE "source" — Standardize + Rank

📄 trips.sql — CTE: source SQL 
WITH source AS (
    SELECT
        *,
        -- Yellow taxis use tpep_*, green use lpep_*. COALESCE picks whichever exists:
        COALESCE(tpep_pickup_datetime, lpep_pickup_datetime) AS pickup_datetime,
        COALESCE(tpep_dropoff_datetime, lpep_dropoff_datetime) AS dropoff_datetime,

        -- Deduplicate: rank rows by how recently they were extracted
        ROW_NUMBER() OVER (
            PARTITION BY
                taxi_type, -- Group identical trips
                COALESCE(tpep_pickup_datetime, lpep_pickup_datetime),
                COALESCE(tpep_dropoff_datetime, lpep_dropoff_datetime),
                pu_location_id, do_location_id,
                fare_amount, total_amount
            ORDER BY extracted_at DESC  -- Keep the newest
        ) AS row_num
    FROM ingestion.trips
    WHERE ... -- filtered to current time window via Jinja templates
)

Why ROW_NUMBER? Because the ingestion layer uses append strategy, re-running a month creates duplicates. ROW_NUMBER() assigns rank 1 to the most recent extraction of each unique trip. The next CTE keeps only rank 1.

Why COALESCE? Yellow and green taxis use different column names for the same data (tpep_* vs lpep_*). COALESCE picks the non-null one, giving us a single standardized pickup_datetime column.

Step 2: CTE "deduplicated" — Filter

📄 trips.sql — CTE: deduplicated SQL 
deduplicated AS (
    SELECT * FROM source WHERE row_num = 1   -- Only keep the "winner" of each group
)

Step 3: Final SELECT — Enrich & Hash

📄 trips.sql — final SELECT SQL 
SELECT
    md5(                              -- Create a unique ID from trip attributes
        CAST(d.taxi_type AS VARCHAR) || '-' ||
        CAST(d.pickup_datetime AS VARCHAR) || '-' ||
        ...
    ) AS trip_id,
    d.pickup_datetime,
    d.dropoff_datetime,
    d.taxi_type,
    d.passenger_count,
    d.trip_distance,
    d.pu_location_id,
    d.do_location_id,
    CAST(d.payment_type AS INTEGER) AS payment_type_id,
    p.payment_type_name,              -- From the JOIN!
    d.fare_amount,
    d.total_amount
FROM deduplicated d
LEFT JOIN ingestion.payment_lookup p  -- Enrich with human-readable names
    ON CAST(d.payment_type AS INTEGER) = p.payment_type_id
md5() Hash
Creates a unique trip_id by hashing multiple columns together. Since the raw data has no natural unique key, we manufacture one. Two identical trips always produce the same hash.
LEFT JOIN
Joins with payment_lookup to translate payment_type=1 into "credit_card". LEFT means: keep all trips even if no matching payment type is found.

Quality Checks on staging.trips

trip_id: not_null + unique
Every row must have a unique identifier.
taxi_type: accepted_values
Only "yellow" or "green" allowed. Catches data corruption.

A trip can't have negative distance.

Reports — The Manager's Summary

reports/trips_report.sql — Daily Aggregates

🏭 Analogy

This is the summary report for the factory manager. Instead of looking at millions of individual trips, the manager wants: "On January 15, how many yellow taxi credit card trips were there? What was the total revenue?" This asset answers those questions.

staging.trips
→
GROUP BY aggregation
→
reports.trips_report
3,000,000 detailed rows
→
~5,000 summary rows
📄 trips_report.sql SQL 
SELECT
    CAST(pickup_datetime AS DATE) AS pickup_date,   -- Group by date (not time)
    taxi_type,                                        -- yellow or green
    payment_type_name,                                -- credit_card, cash, etc.
    COUNT(*) AS trip_count,                           -- How many trips?
    SUM(passenger_count) AS total_passengers,           -- Total passengers
    SUM(trip_distance) AS total_distance,               -- Total miles driven
    SUM(fare_amount) AS total_fare,                     -- Total fare collected
    SUM(total_amount) AS total_amount                    -- Total amount charged
FROM staging.trips
WHERE pickup_datetime >= '{{ start_datetime }}'
  AND pickup_datetime < '{{ end_datetime }}'
GROUP BY
    CAST(pickup_datetime AS DATE),
    taxi_type,
    payment_type_name

What GROUP BY Does

Imagine you have 3 million rows of individual trips. GROUP BY collapses them into groups where every row shares the same date + taxi type + payment method. Then the aggregate functions (COUNT, SUM) compute summaries for each group.

Jinja Templates
{{ start_datetime }} and {{ end_datetime }} are replaced by Bruin with the current run's time window. This is how incremental processing works in SQL assets.
Composite Primary Key
pickup_date + taxi_type + payment_type_name together form the primary key. Each unique combination gets exactly one summary row.
non_negative checks
Trip count, distance, and passengers can never be negative. These checks catch bugs in upstream logic.

Reference

Jargon Glossary

Every technical term used in this pipeline, explained in plain English.

Asset
A single unit of work in the pipeline — a SQL query, a Python script, or a CSV seed. Each asset produces one database table or view.
Pipeline
A collection of assets that run together on a schedule. Defined by a pipeline.yml file. Think of it as the entire factory.
Materialization
The act of writing query results to a physical database table. "Materializing" an asset means running its code and saving the output.
Strategy: append
Always insert new rows, never touch existing ones. Simple but can create duplicates if the same data is processed twice.
Strategy: time_interval
Only process data within the current time window. Deletes old data for that window first, then inserts new data. Prevents duplicates for reprocessed periods.
Strategy: merge
Upsert strategy — insert new rows, update existing ones (matched by primary key). Not used in this pipeline but common in Bruin.
Seed
A static CSV file loaded directly into the database. Used for small reference/lookup data that rarely changes.
Incremental Key
The column used to identify which rows are "new" in time_interval strategy. Usually a timestamp like pickup_datetime.
Quality Checks
Automated validations that run after an asset materializes. If a check fails, the pipeline alerts you. Examples: not_null, unique, non_negative.
Full Refresh
Reprocessing ALL data from scratch, ignoring incremental logic. Used when you change business logic and need to recompute historical data.
Backfill
Processing historical time windows that were missed or need reprocessing. E.g., running the pipeline for every month from Jan 2022 to Dec 2023.
Lineage / DAG
The dependency graph showing which assets depend on which. A DAG (Directed Acyclic Graph) ensures assets run in the correct order. Defined by depends declarations.
Dependencies
Assets that must finish before another can start. staging.trips depends on ingestion.trips, so ingestion always runs first.
Environment
A named configuration set (e.g., "default", "production"). Each environment can have different database connections, letting you test without affecting production.
Connection
A named reference to an external system (database, API, etc.). Defined in .bruin.yml so assets don't hardcode credentials.
Parquet
A columnar file format designed for analytics. Stores data by column (not row), enabling fast reads and excellent compression. The NYC TLC publishes data in this format.
CTE (Common Table Expression)
A WITH ... AS (...) clause in SQL. Creates a temporary, named result set you can reference later in the query. Like a variable for SQL.
Jinja Templates
{{ start_datetime }} syntax in SQL. Bruin replaces these placeholders with actual values before running the query. Used for dynamic time filtering.
