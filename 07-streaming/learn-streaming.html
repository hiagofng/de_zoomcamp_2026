Learn Streaming

An interactive, illustrated guide to real-time data streaming — built from your own code in 07-streaming/.

Imagine a restaurant kitchen. In batch processing, you wait until all 50 orders arrive, then cook them all at once at midnight. In stream processing, you start cooking each order the moment it comes in. The food arrives fresher, and the kitchen stays busy instead of idle.

That's the core idea: process data as it arrives, not in big delayed chunks.

Batch vs Streaming

Think of email vs. live chat.

  • Batch = Email. You collect all messages, read them at the end of the day, and reply in bulk.
  • Streaming = Live chat. Each message arrives instantly, you respond immediately, and the conversation flows in real-time.

Your project uses streaming: each taxi ride is sent as a message the moment it's ready, and the consumer reads it immediately.

What is Kafka / Redpanda?

Apache Kafka is a distributed system designed to handle real-time data streams. Think of it as a super-powered post office for data.

Redpanda is what your project uses — it's a drop-in replacement for Kafka that's simpler to run (no Java, no Zookeeper). It speaks the exact same "language" (protocol), so all Kafka tools and libraries work with it.

The Post Office Analogy:

  • Kafka/Redpanda = The post office building
  • Topics = Mailboxes (labeled categories like "rides", "payments")
  • Producers = People dropping off letters (your producer.ipynb)
  • Consumers = People picking up letters (your consumer.ipynb)
  • Messages = The letters themselves (taxi ride data)

The post office stores letters safely until someone picks them up. Even if nobody is picking up mail right now, the letters don't get lost.

Why not just use a database?

Database

Designed for storing and querying data. You ask: "Give me all rides from yesterday." The DB searches and returns results.

Like a filing cabinet — great for looking things up, but nobody notifies you when a new file is added.

Kafka / Redpanda

Designed for moving data between systems in real-time. It's not about querying — it's about reliably delivering messages from A to B.

Like a conveyor belt — items flow through continuously, and anyone can watch and grab what they need.

The key insight: The producer and consumer are completely independent. The producer can send 1,000 messages while the consumer is offline. When the consumer starts, it reads from where it left off. They don't need to be running at the same time. Redpanda is the reliable middleman that holds the data.

Topics & Partitions

Topics

A topic is just a named stream of messages. It's like a TV channel: the producer "broadcasts" on a channel, and consumers "tune in" to that channel.

In your code, the topic is called "rides". You could have other topics like "payments", "alerts", etc.

Partitions

Each topic can be split into partitions. Think of it like lanes on a highway:

Highway lanes analogy: A 3-lane highway moves more cars than a 1-lane road. Similarly, 3 partitions allow 3 consumers to read in parallel, giving you 3x throughput. But just like cars can arrive in different orders across lanes, messages across partitions don't have a guaranteed global order.

Your project uses 1 partition (the default), which is fine for learning. In production, you'd increase this for higher throughput.

Offsets

Every message in a partition gets a sequential number called an offset. It starts at 0 and increments by 1 for each new message. It never resets, never goes backwards, and never has gaps.

Why offsets matter: The consumer remembers which offset it last read. If it crashes and restarts, it picks up exactly where it left off — no missed messages, no duplicates. This is called a committed offset.

In your code, auto_offset_reset='earliest' means: "If I have no saved position, start reading from offset 0 (the very beginning)."

Bookmark analogy: An offset is like a bookmark in a book. If you close the book (stop the consumer), you can open it later and continue from the bookmark. earliest means "start from page 1 if there's no bookmark." The alternative, latest, means "skip to the last page and only read new pages."

Consumer Groups

A consumer group is a team of consumers that share the work of reading a topic. Kafka ensures each message is delivered to exactly one consumer in the group.

Pizza delivery team analogy:

  • Within a group: Like delivery drivers splitting up orders. If 30 orders come in, Driver A takes orders 1-10, Driver B takes 11-20, Driver C takes 21-30. Each order goes to exactly one driver. More drivers = faster delivery.
  • Across groups: Like having both a delivery team AND an analytics team. The delivery team processes orders to fulfill them. The analytics team reads the same orders to build reports. Each team gets ALL the data.

In your consumer.ipynb, the group ID is "rides-console":

consumer = KafkaConsumer(
    topic_name,
    group_id='rides-console',  # This consumer belongs to group "rides-console"
    ...
)

If you launched two notebooks with the same group ID, they'd split the work. If you use a different group ID, both would get every message independently.

Docker Compose Deep Dive

Your docker-compose.yaml starts Redpanda in a container. Let's break it down line by line:

services:
  redpanda:                         # Name of the service
    image: redpandadata/redpanda:v25.3.9  # The Docker image to use
    command:                          # Configuration flags:
      - redpanda start
      - --smp 1                       # Use 1 CPU core (saves resources)
      - --reserve-memory 0M           # Don't reserve extra memory
      - --overprovisioned             # Tell Redpanda: "resources are limited, be gentle"
      - --node-id 1                   # This broker's ID (useful if you had multiple)

      # KAFKA ADDRESSES (how clients connect):
      - --kafka-addr
        PLAINTEXT://0.0.0.0:29092,    # Internal (other containers)
        OUTSIDE://0.0.0.0:9092        # External (your notebooks on localhost)
      - --advertise-kafka-addr
        PLAINTEXT://redpanda:29092,   # Tell internal clients: "find me at redpanda:29092"
        OUTSIDE://localhost:9092      # Tell external clients: "find me at localhost:9092"

    ports:                            # Map container ports to your machine
      - 9092:9092                    # Kafka protocol (YOUR NOTEBOOKS USE THIS)
      - 8082:8082                    # HTTP Proxy (REST API)

The two-door analogy: Redpanda has two "doors" for Kafka connections:

  • Port 29092 (Internal door): For other Docker containers. Like an employee entrance.
  • Port 9092 (External door): For programs running on your machine (like your Jupyter notebooks). Like the public entrance.

Your notebooks connect to localhost:9092 because they run on your machine, not inside Docker.

The Ride Data Model

Your models.py defines what a taxi ride looks like as a Python object:

from dataclasses import dataclass

@dataclass                    # This decorator auto-generates __init__, __repr__, etc.
class Ride:
    PULocationID: int         # Pickup location (zone number)
    DOLocationID: int         # Dropoff location (zone number)
    trip_distance: float     # Distance in miles
    total_amount: float      # Total fare in dollars
    tpep_pickup_datetime: int # Pickup time as epoch milliseconds

What is a @dataclass?

Form template analogy: A dataclass is like a standardized form. Instead of passing around random notes about taxi rides, you create a template with specific fields. Every ride must fill in the same fields: pickup location, dropoff location, distance, amount, and time.

Without @dataclass, you'd have to write much more code:

Without @dataclass

class Ride:
  def __init__(self, PULocationID,
    DOLocationID, trip_distance,
    total_amount,
    tpep_pickup_datetime):
      self.PULocationID = PULocationID
      self.DOLocationID = DOLocationID
      self.trip_distance = trip_distance
      self.total_amount = total_amount
      self.tpep_pickup_datetime = \
        tpep_pickup_datetime

With @dataclass

@dataclass
class Ride:
    PULocationID: int
    DOLocationID: int
    trip_distance: float
    total_amount: float
    tpep_pickup_datetime: int




# Python auto-generates __init__!

What is epoch milliseconds?

Epoch time is the number of seconds (or milliseconds) since January 1, 1970, 00:00:00 UTC. It's a universal way to represent time as a single number.

Example: 1761956005000 milliseconds = November 1, 2025, around midnight

Why use this? Because different systems and countries format dates differently (MM/DD/YYYY vs DD/MM/YYYY), but a number is universal. No ambiguity.

# This is how your code converts a datetime to epoch ms:
int(row['tpep_pickup_datetime'].timestamp() * 1000)
#                                 ^^^^^^^^^^^          ^^^^
#                                 seconds since 1970   * 1000 = milliseconds

Serialization & Deserialization

Networks can only transmit bytes (raw 0s and 1s). Your Python Ride object lives in memory — it can't travel over a network. So we need to convert it.

Language translation analogy: Imagine you speak Portuguese but need to send a letter to someone in Japan. You can't just send your thoughts directly — you need to:

  1. Serialize: Translate your thoughts into a written letter (Portuguese → universal format)
  2. Send: Mail the letter
  3. Deserialize: The recipient translates the letter into Japanese to understand it

In code: Python object → JSON bytes → (sent via Kafka) → JSON bytes → Python dict/object

Your serializer (in producer):

def ride_serializer(ride):
    rides_dict = dataclasses.asdict(ride)   # Step 1: Ride object → Python dictionary
    ride_json = json.dumps(rides_dict)      # Step 2: Dictionary → JSON string
                    .encode('utf-8')       # Step 3: String → bytes
    return ride_json

Your deserializer (in consumer):

# In consumer.ipynb, done inline with a lambda:
value_deserializer=lambda x: json.loads(x.decode('utf-8'))
#                                       ^^^^^^^^^^^^^^^^  bytes → string
#                           ^^^^^^^^^^                    string → dictionary

Producer Notebook - Line by Line

The producer's job: read taxi data → convert to Ride objects → send to Redpanda.

Step 1: Download the data
import pandas as pd

url = "https://d37ci6vzurychx.cloudfront.net/trip-data/yellow_tripdata_2025-11.parquet"
columns = ['PULocationID', 'DOLocationID', 'trip_distance', 'total_amount', 'tpep_pickup_datetime']
df = pd.read_parquet(url, columns=columns).head(1000)

What happens: Pandas downloads a Parquet file (a compressed column-based file format, much more efficient than CSV) from the NYC Taxi & Limousine Commission website. It reads only 5 specific columns and takes the first 1,000 rows.

Result: A DataFrame (think: a spreadsheet in Python) with 1,000 taxi rides.

Step 2: Convert a row to a Ride
ride = ride_from_row(df.iloc[1])
# Result: Ride(PULocationID=142, DOLocationID=237, trip_distance=2.28,
#              total_amount=24.94, tpep_pickup_datetime=1761958147000)

What happens: df.iloc[1] grabs the 2nd row (index starts at 0). ride_from_row() extracts the values, converts the datetime to epoch milliseconds, and creates a Ride object.

Step 3: Create the Kafka Producer
from kafka import KafkaProducer

server = 'localhost:9092'
producer = KafkaProducer(
    bootstrap_servers=server,        # Where is Redpanda?
    value_serializer=ride_serializer  # How to convert Ride → bytes
)

What happens: Creates a connection to Redpanda. The value_serializer tells the producer: "Every time I send a message, first run it through ride_serializer to convert it to bytes."

This is automatic — you just pass a Ride object to send() and the serializer handles the conversion behind the scenes.

Step 4: Send a message
topic_name = 'rides'

producer.send(topic_name, value=ride)  # Send the ride to the "rides" topic
producer.flush()                        # Force-send everything NOW (don't buffer)

What happens:

  1. send() puts the message in an internal buffer (like an outbox). The serializer converts ride to bytes automatically.
  2. flush() forces the producer to actually transmit all buffered messages to Redpanda. Without flush(), the producer might wait and batch multiple messages together for efficiency.

The producer currently only sends one ride. To send all 1,000, you'd loop through the DataFrame:

for _, row in df.iterrows():
    ride = ride_from_row(row)
    producer.send(topic_name, value=ride)
producer.flush()  # Send all remaining buffered messages

Consumer Notebook - Line by Line

The consumer's job: connect to Redpanda → read messages from the "rides" topic → convert bytes back to Python data.

Step 1: Import the model
from kafka import KafkaConsumer
import json
from models import Ride, ride_deserializer

Imports the Ride class and deserializer from models.py (the shared file).

Step 2: Create the Consumer
consumer = KafkaConsumer(
    'rides',                        # Subscribe to the "rides" topic
    bootstrap_servers=['localhost:9092'],  # Where is Redpanda?
    auto_offset_reset='earliest',   # Start from the beginning if no saved position
    group_id='rides-console',        # This consumer's team name
    value_deserializer=lambda x: json.loads(x.decode('utf-8'))
    #                   ^^^^^^^^ anonymous function that converts bytes → dict
)

Let's unpack each parameter:

  • 'rides' — The topic to listen to. Only messages sent to this topic will be received.
  • bootstrap_servers — The address of Redpanda. "Bootstrap" means the first server to ask for the cluster layout.
  • auto_offset_reset='earliest' — "If I've never read this topic before, start from message #0." Alternative: 'latest' (only see new messages from now on).
  • group_id='rides-console' — Identifies which consumer group this belongs to. Redpanda tracks what this group has already read.
  • value_deserializer — The reverse of the producer's serializer. Converts raw bytes back to a Python dict.
Step 3: Read a message
next(consumer)  # Get the next available message

What happens: next() pulls the next message from the topic. If no messages are available, it waits (blocks) until one arrives. The result is a ConsumerRecord containing:

ConsumerRecord(
  topic='rides',
  partition=0,              # Which partition it came from
  offset=0,                 # Message number within that partition
  timestamp=1773264348489,  # When Redpanda received it
  key=None,                 # No key was set by the producer
  value={                    # The actual ride data (already deserialized!)
    'PULocationID': 1,
    'DOLocationID': 10,
    'trip_distance': 10,
    'total_amount': 20,
    'tpep_pickup_datetime': 1761956005000
  }
)

The consumer is an iterator. You can also use a for loop to continuously read messages:

for message in consumer:
    print(message.value)  # Process each ride as it arrives
    # This loop runs FOREVER, waiting for new messages

This is the core of stream processing: an infinite loop that reacts to each message as it arrives.

TV remote analogy:

  • next(consumer) is like pressing "Next channel" once — you see one thing.
  • for message in consumer is like leaving the TV on — you see everything that comes on, forever.
