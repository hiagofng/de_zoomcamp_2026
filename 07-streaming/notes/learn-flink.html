Why Not Just Use Kafka Consumers?

In Part 1, you built a Python consumer that reads rides from Kafka and could insert them into PostgreSQL. That works! But what if you need more?

What your Python consumer CAN'T easily do

  • Time windows — "Count trips per hour" requires you to track buckets, handle clock time, and decide when to publish results
  • Late events — What if a ride arrives 10 seconds late? Your hourly count was already published
  • Crash recovery — If your script crashes mid-batch, where do you restart?
  • Parallelism — Processing 1M events/sec on a single Python process is impossible

What Flink gives you for free

  • Built-in windows — tumbling, sliding, session — one line of SQL
  • Watermarks — automatic handling of late data
  • Checkpointing — crash-proof state recovery
  • Parallel workers — distribute across machines
  • Connectors — Kafka, JDBC, filesystem — no psycopg2 code

Home cooking vs. restaurant kitchen: Your Python consumer is like cooking at home — you do everything manually: chop, cook, plate, clean. Flink is a professional kitchen with a head chef (JobManager), line cooks (TaskManagers), prep stations (task slots), and dishwashers (connectors). You just write the recipe (SQL), and the kitchen handles the rest.

Flink Architecture

Airport analogy:

  • JobManager = Air Traffic Control tower. It doesn't fly planes, but it tells each plane where to go, manages schedules, and handles emergencies.
  • TaskManager = The runway terminal. It has multiple gates (task slots) where planes (pipeline stages) can dock.
  • Task Slots = Individual gates. Each gate can handle one flight (one parallel copy of your pipeline). More gates = more flights at once.
  • Parallelism = 3 = You're running 3 copies of the same flight route simultaneously — 3 planes flying the same route for 3x the passenger capacity.

The Dockerfile

Flink doesn't come with Python support. Your Dockerfile.flink builds a custom image that adds everything needed:

# Start from the official Flink image (Java-based)
FROM flink:2.2.0-scala_2.12-java17

# Install 'uv' (fast Python package manager)
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/

# Install Python 3.12 and PyFlink
WORKDIR /opt/pyflink
COPY pyproject.flink.toml pyproject.toml
RUN uv python install 3.12 && uv sync

# Download connector JARs (Java libraries)
WORKDIR /opt/flink/lib
RUN wget ...flink-json-2.2.0.jar;         # Parse JSON messages
    wget ...flink-sql-connector-kafka...jar; # Read from Kafka
    wget ...flink-connector-jdbc-core...jar; # Write to databases
    wget ...flink-connector-jdbc-postgres...; # PostgreSQL specifics
    wget ...postgresql-42.7.10.jar           # PostgreSQL JDBC driver

# Apply custom Flink config
COPY flink-config.yaml /opt/flink/conf/config.yaml

Toolbox analogy: Flink is like buying a workbench (the base image). It comes with basic tools (Java, Scala). But you need to add your own power tools:

  • Python + PyFlink = a drill, so you can write jobs in Python instead of Java
  • Kafka connector JAR = a special attachment to read data from Kafka
  • JDBC connector JAR = another attachment to write data to databases
  • PostgreSQL driver = the specific bit that speaks PostgreSQL's language

Without these JARs, Flink wouldn't know HOW to talk to Kafka or PostgreSQL. The JARs are like translation dictionaries.

What is a JAR? A JAR (Java ARchive) is a package of compiled Java code — like a .zip file full of Java classes. Since Flink runs on the JVM (Java Virtual Machine), its plugins come as JARs. You don't write Java — PyFlink lets you use Python — but under the hood, Flink still uses these Java libraries to connect to external systems.

Docker Compose — Flink Services

Your docker-compose.yaml defines two Flink services. Let's break them down:

JobManager (The Boss)

jobmanager:
  build:
    context: .                      # Build from current directory
    dockerfile: ./Dockerfile.flink  # Using our custom Dockerfile
  image: pyflink-workshop           # Tag the built image as "pyflink-workshop"
  pull_policy: never               # Don't try Docker Hub - this image is local only
  expose:
    - "6123"                       # RPC port (internal, for TaskManagers to connect)
  ports:
    - "8081:8081"                  # Web UI - open localhost:8081 in your browser!
  volumes:
    - ./:/opt/flink/usrlib          # Mount entire project directory
    - ./src/:/opt/src               # Mount source code (your .py job files)
  command: jobmanager              # Start as JobManager role
  environment:
    - |
      FLINK_PROPERTIES=
      jobmanager.rpc.address: jobmanager      # "I am reachable at hostname 'jobmanager'"
      jobmanager.memory.process.size: 1600m   # 1.6 GB of RAM

TaskManager (The Worker)

taskmanager:
  image: pyflink-workshop            # Reuse the same image (no rebuild!)
  pull_policy: never
  depends_on:
    - jobmanager                     # Start AFTER JobManager is up
  command: taskmanager --taskmanager.registration.timeout 5 min
  #                   ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
  #        Give it 5 minutes to find the JobManager (services start in parallel)
  volumes:
    - ./:/opt/flink/usrlib
    - ./src/:/opt/src                # Same mount - so it can access your .py files
  environment:
    - |
      FLINK_PROPERTIES=
      jobmanager.rpc.address: jobmanager       # "The boss is at hostname 'jobmanager'"
      taskmanager.memory.process.size: 1728m   # 1.7 GB of RAM
      taskmanager.numberOfTaskSlots: 15        # I have 15 slots available
      parallelism.default: 3                   # Default: run 3 copies of each stage

Why pull_policy: never? The image pyflink-workshop doesn't exist on Docker Hub — you built it locally. Without never, Docker would try to download it from the internet and fail.

Why mount ./src/:/opt/src? This maps your local src/ folder into the container at /opt/src. When you edit pass_through_job.py on your laptop, the changes are instantly visible inside the container. No need to rebuild the Docker image every time you change your code!

Slots & Parallelism

Supermarket checkout analogy:

  • Task Slots = checkout lanes. Your store has 15 lanes.
  • Parallelism = 3 means each "job" (like handling online orders) uses 3 lanes. Three cashiers process orders simultaneously — 3x faster.
  • With 15 lanes and 3 per job, you can run 5 different jobs at once.
  • If you only have 1 job running (like now), 12 lanes sit idle — that's fine for development.

Parallelism can't exceed partition count! If your Kafka topic has 1 partition and you set parallelism to 3, only 1 of the 3 copies will actually receive data. The other 2 will sit idle. For full parallelism, you need at least as many Kafka partitions as your parallelism setting.

Flink SQL — The Core Idea

Here's the key insight about Flink: you don't write processing logic in Python. Instead, you write SQL, and Flink translates that SQL into a streaming pipeline.

A Flink job has 3 parts:

  1. Source table (CREATE TABLE) — "where does data come from?" (Kafka)
  2. Sink table (CREATE TABLE) — "where does data go?" (PostgreSQL)
  3. Query (INSERT INTO ... SELECT) — "what transformation to apply?"

That's it. Flink handles everything else: connecting, reading, writing, retrying, checkpointing.

Plumbing analogy: Think of it as connecting pipes:

  • Source = the water tank (Kafka). You describe where it is and what the water looks like (JSON format, which fields).
  • Sink = the faucet (PostgreSQL). You describe where to deliver and what shape the output should be.
  • Query = the pipe route and any filters/valves in between. INSERT INTO sink SELECT ... FROM source is the pipe connecting tank to faucet.

Kafka Source Table

This SQL tells Flink: "There's a Kafka topic called rides with JSON messages that have these fields."

CREATE TABLE events (
    PULocationID INTEGER,              -- Pickup zone (matches JSON field name exactly)
    DOLocationID INTEGER,              -- Dropoff zone
    trip_distance DOUBLE,             -- Miles
    total_amount DOUBLE,              -- Fare in dollars
    tpep_pickup_datetime BIGINT      -- Epoch milliseconds (a big number)
) WITH (
    'connector' = 'kafka',                          -- Use the Kafka connector JAR
    'properties.bootstrap.servers' = 'redpanda:29092', -- INTERNAL Docker address!
    'topic' = 'rides',                               -- The Kafka topic name
    'scan.startup.mode' = 'latest-offset',           -- Only read NEW messages
    'properties.auto.offset.reset' = 'latest',       -- Fallback: also latest
    'format' = 'json'                                -- Messages are JSON encoded
);

Notice: redpanda:29092 not localhost:9092!

Flink runs inside Docker. From inside Docker, containers find each other by service name. So Flink uses redpanda:29092 (the internal Docker door). Your Jupyter notebooks used localhost:9092 because they run on your laptop (the external door).

Column names MUST match the JSON keys exactly. When your producer sends {"PULocationID": 43, ...}, Flink matches the JSON key "PULocationID" to the column PULocationID. If you typed pu_location_id instead, Flink would get NULL — it wouldn't find a matching JSON key.

PostgreSQL Sink Table

CREATE TABLE processed_events (
    PULocationID INTEGER,
    DOLocationID INTEGER,
    trip_distance DOUBLE,
    total_amount DOUBLE,
    pickup_datetime TIMESTAMP        -- Converted from epoch to human-readable!
) WITH (
    'connector' = 'jdbc',                                    -- JDBC connector JAR
    'url' = 'jdbc:postgresql://postgres:5432/postgres',       -- Internal Docker address
    'table-name' = 'processed_events',                       -- Actual PostgreSQL table name
    'username' = 'postgres',
    'password' = 'postgres',
    'driver' = 'org.postgresql.Driver'                      -- The JDBC driver class
);

What is JDBC? JDBC (Java Database Connectivity) is a standard Java API for connecting to databases. It's like a universal power adapter — one interface that works with PostgreSQL, MySQL, Oracle, etc. Each database provides its own "driver" (like org.postgresql.Driver) that translates JDBC calls into that database's specific protocol.

You don't write JDBC code — Flink uses it behind the scenes. You just declare the connection details and Flink handles the INSERT statements automatically.

Compare this to your Python consumer approach:

Python consumer (manual)

import psycopg2
conn = psycopg2.connect(...)
cur = conn.cursor()
for msg in consumer:
  cur.execute("INSERT INTO ...",
    (ride.PULocationID, ...))
# You handle: connection, SQL,
# retries, commits, errors

Flink (declarative)

CREATE TABLE processed_events
  (...) WITH (
    'connector' = 'jdbc', ...
  );

-- That's it. Flink handles
-- connection, batching, retries,
-- commits, error recovery.

The Full Pass-Through Pipeline

Now let's see how the three parts connect in pass_through_job.py:

from pyflink.datastream import StreamExecutionEnvironment
from pyflink.table import EnvironmentSettings, StreamTableEnvironment

def log_processing():
    # Step 1: Create the Flink "world"
    env = StreamExecutionEnvironment.get_execution_environment()
    env.enable_checkpointing(10 * 1000)  # Save state every 10 seconds

    # Step 2: Create a SQL-capable environment
    settings = EnvironmentSettings.new_instance().in_streaming_mode().build()
    t_env = StreamTableEnvironment.create(env, environment_settings=settings)

    # Step 3: Declare source (Kafka) and sink (PostgreSQL)
    source_table = create_events_source_kafka(t_env)       # "events"
    postgres_sink = create_processed_events_sink_postgres(t_env) # "processed_events"

    # Step 4: The actual pipeline - just SQL!
    t_env.execute_sql(f"""
        INSERT INTO {postgres_sink}
        SELECT
            PULocationID,
            DOLocationID,
            trip_distance,
            total_amount,
            TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3) as pickup_datetime
        FROM {source_table}
    """).wait()

if __name__ == '__main__':
    log_processing()

What is TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3)?

This converts epoch milliseconds to a human-readable timestamp:

  • TO_TIMESTAMP_LTZ = "To Timestamp with Local Time Zone"
  • The 3 means the input is in milliseconds precision (10-3 seconds)
  • Input: 1730420005000 → Output: 2025-11-01 00:13:25.000

What does .wait() do? Without it, the Python script would exit immediately after submitting the SQL, and the job might not start properly. .wait() tells Python: "Block here and keep running until the Flink job finishes (or forever, since streaming jobs never finish on their own)."

How to submit the job

# On Windows with Git Bash, use MSYS_NO_PATHCONV=1 to prevent path mangling
MSYS_NO_PATHCONV=1 docker compose exec jobmanager ./bin/flink run \
    -py /opt/src/job/pass_through_job.py \
    --pyFiles /opt/src -d

Breaking this down:

  • docker compose exec jobmanager — run a command inside the jobmanager container
  • ./bin/flink run — the Flink CLI command to submit a job
  • -py /opt/src/job/pass_through_job.py — the Python file to run
  • --pyFiles /opt/src — additional Python files to include (like models.py)
  • -d — detached mode (run in background, return immediately)

Checkpointing

env.enable_checkpointing(10 * 1000)  # every 10,000 milliseconds = 10 seconds

Video game save points: Imagine you're playing a long RPG. If you don't save and the power goes out, you lose all your progress and start from the beginning. But if you save every 10 minutes, you only lose 10 minutes of progress.

Checkpointing is Flink's auto-save. Every 10 seconds, it saves:

  • Which Kafka offsets have been read (like your position in the game)
  • Any data currently being processed in windows (like items in your inventory)

If the job crashes and restarts, it loads the last checkpoint and continues from there — no data lost, no duplicates.

Checkpoints are scoped to a job instance. If you cancel a job and submit a new one, the new job has NO access to the old job's checkpoints. It starts fresh. This is why canceling + resubmitting with earliest-offset reprocesses everything.

To preserve state across restarts, restart the existing job instead of creating a new one.

Windowed Aggregation

Now comes the really powerful part. Instead of just passing data through, let's aggregate: count trips and sum revenue per pickup location, per hour.

The problem: In batch processing, you'd run a query like:

SELECT PULocationID, COUNT(*), SUM(total_amount)
FROM rides
WHERE pickup_time BETWEEN '14:00' AND '15:00'
GROUP BY PULocationID;

Easy — all the data is already there. But in streaming, events arrive one at a time. You can't just wait until 3 PM to count the 2-3 PM window because events might arrive late. When do you publish the result?

This requires three new concepts working together:

Watermarks — The Hardest Concept

This is the concept that trips up most people. Let's go step by step.

The teacher collecting homework analogy:

Imagine a teacher collecting essays. The deadline is 3:00 PM.

  • At 3:00 PM sharp, most students have turned in their work.
  • But the teacher knows some students always run a few minutes late (stuck in traffic, printer jam, etc.).
  • So the teacher waits 5 extra minutes before grading — this is the watermark delay!
  • At 3:05 PM, the teacher says "OK, I'm grading now. Anyone submitting after this gets a separate correction round."

In Flink:

  • The "deadline" is the end of a time window (e.g., 3:00 PM)
  • The "5 extra minutes" is the watermark delay (INTERVAL '5' SECOND)
  • "Grading" is publishing the window results to PostgreSQL
  • "Separate correction round" is the upsert (updating the already-published count)
-- In the Kafka source table of aggregation_job.py:
event_timestamp AS TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3),
--              ^^                                          ^
-- Computed column: converts epoch ms to timestamp       precision=ms

WATERMARK FOR event_timestamp AS event_timestamp - INTERVAL '5' SECOND
--                                                ^^^^^^^^^^^^^^^^^^^^
--              "My patience is 5 seconds. After that, publish the window."

How the watermark moves:

The watermark is always = (latest event timestamp seen) minus 5 seconds.

  • Flink sees event with ts=14:00:12 → watermark = 14:00:07
  • Flink sees event with ts=14:00:18 → watermark = 14:00:13
  • Flink sees event with ts=14:00:25 → watermark = 14:00:20

When the watermark passes the end of a window (e.g., 15:00:00), Flink says "the 14:00-15:00 window is complete" and publishes the results.

Tumbling Windows

Your aggregation job uses tumbling windows — the simplest type.

-- The magic line in aggregation_job.py:
FROM TABLE(
    TUMBLE(
        TABLE {source_table},            -- Read from this table
        DESCRIPTOR(event_timestamp),     -- Use this column as the "clock"
        INTERVAL '1' HOUR              -- Each window is 1 hour wide
    )
)
GROUP BY window_start, PULocationID;  -- Group by window AND location

The TUMBLE function automatically:

  • Creates 1-hour buckets based on the event_timestamp column
  • Assigns each event to its bucket (e.g., 14:23 → the [14:00, 15:00) bucket)
  • Makes window_start available as a column in your SELECT

Upserts & PRIMARY KEY

What happens if a late event arrives after the window result was already written to PostgreSQL?

Without PRIMARY KEY (append-only)

Flink writes: trips=5 for the 2 PM window

Late event arrives.

Flink writes: trips=6 as a new row

Result: TWO rows for the same window. Your counts are wrong (5+6=11 instead of 6).

With PRIMARY KEY (upsert)

Flink writes: trips=5 for the 2 PM window

Late event arrives.

Flink writes: trips=6 and PostgreSQL updates the existing row

Result: ONE correct row with trips=6.

-- The sink table with PRIMARY KEY for upsert:
CREATE TABLE processed_events_aggregated (
    window_start TIMESTAMP(3),
    PULocationID INT,
    num_trips BIGINT,
    total_revenue DOUBLE,
    PRIMARY KEY (window_start, PULocationID) NOT ENFORCED
    --           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    -- Unique combo of window + location = enables upsert
) WITH ( ... );

What does NOT ENFORCED mean? It tells Flink: "I'm declaring a primary key for upsert behavior, but don't bother checking uniqueness on the Flink side — let PostgreSQL handle that." Flink uses this information to generate INSERT ... ON CONFLICT UPDATE SQL statements instead of plain INSERT.

Scoreboard analogy: Think of a sports scoreboard. Without upsert, every score update adds a NEW line to the board: "Team A: 1", "Team A: 2", "Team A: 3". With upsert (PRIMARY KEY), the board UPDATES the existing line: "Team A: 3" — always showing the latest correct score.

Aggregation Job — Complete Walkthrough

Now let's see everything together in aggregation_job.py:

Step 1: Kafka Source with Watermark

Two new lines compared to the pass-through job:

event_timestamp AS TO_TIMESTAMP_LTZ(tpep_pickup_datetime, 3),
-- Computed column: epoch ms → real timestamp

WATERMARK FOR event_timestamp AS event_timestamp - INTERVAL '5' SECOND
-- "Wait 5 seconds for late events before publishing windows"

Also uses earliest-offset to process all existing data in the topic.

Step 2: PostgreSQL Sink with PRIMARY KEY

Defines the output table with a composite primary key:

PRIMARY KEY (window_start, PULocationID) NOT ENFORCED

This means: for each combination of (hour, pickup location), there's exactly one row. Late events update it rather than creating duplicates.

Step 3: The Pipeline
INSERT INTO processed_events_aggregated
SELECT
    window_start,                          -- Start of the 1-hour bucket
    PULocationID,                          -- Pickup zone
    COUNT(*) AS num_trips,                -- How many trips in this bucket
    SUM(total_amount) AS total_revenue    -- Total fare for this bucket
FROM TABLE(
    TUMBLE(TABLE events, DESCRIPTOR(event_timestamp), INTERVAL '1' HOUR)
)
GROUP BY window_start, PULocationID;

Read this as: "For each 1-hour window and each pickup location, count the rides and sum the fares, then write to PostgreSQL."

Step 4: Additional Configuration
env.enable_checkpointing(10 * 1000)   # Auto-save every 10 seconds
env.set_parallelism(3)                 # Run 3 copies processing in parallel

Window Types

1. Tumbling Windows (your code uses this)

Use case: "Count trips per hour," "daily revenue summary."

TUMBLE(TABLE events, DESCRIPTOR(event_timestamp), INTERVAL '1' HOUR)

2. Sliding (Hop) Windows

Use case: "What was the peak traffic in any 1-hour period?" Great for surge pricing, moving averages.

HOP(TABLE events, DESCRIPTOR(event_timestamp), INTERVAL '15' MINUTE, INTERVAL '1' HOUR)
--                                                slide every 15m     window size 1h

3. Session Windows

Use case: "Group all user clicks into sessions" (a session ends after 30 min of inactivity).

Window types as conversations:

  • Tumbling = Scheduled meetings. 9 AM standup, 10 AM review, 11 AM planning. Fixed time, no overlap.
  • Sliding = Security camera with overlapping footage. Camera 1 covers 9-10, Camera 2 covers 9:15-10:15, Camera 3 covers 9:30-10:30. Every moment is captured by multiple cameras.
  • Session = Phone calls. A call starts when someone picks up and ends when there's been silence for too long. Each call is a different length.

Late Events Deep Dive

Let's trace through exactly what happens when an event arrives late:

The watermark delay is your "patience budget."

  • Small delay (1 sec): Results come fast, but late events may be missed or cause corrections.
  • Large delay (60 sec): Very patient — almost all late events are captured. But you wait a full minute before seeing any results.
  • Your setting (5 sec): A balanced default. Events up to 5 seconds late are always captured within the window. Later events trigger an upsert correction.

The Realtime Producer

Your producer_realtime.py generates fake taxi rides with current timestamps. ~20% of events are intentionally delayed to simulate real-world lateness.

def make_ride(delay_seconds=0):
    now_ms = int(time.time() * 1000) - delay_seconds * 1000
    #                                   ^^^^^^^^^^^^^^^^^^^^
    # Subtracts delay to simulate a "late" event timestamp
    return Ride(
        PULocationID=random.choice(PICKUP_LOCATIONS),  # Random NYC zone
        DOLocationID=random.choice(DROPOFF_LOCATIONS),
        trip_distance=round(random.uniform(0.5, 20.0), 2),
        total_amount=round(random.uniform(5.0, 100.0), 2),
        tpep_pickup_datetime=now_ms,  # Current time minus delay
    )

# In the main loop:
if random.random() < 0.2:              # 20% chance
    delay = random.randint(3, 10)     # 3-10 seconds late
    ride = make_ride(delay_seconds=delay)
    print(f"  LATE ({delay}s) -> PU={ride.PULocationID}")
else:
    ride = make_ride()                 # On time
    print(f"  on time   -> PU={ride.PULocationID}")

producer.send(topic_name, value=ride)
time.sleep(0.5)  # Send 2 events per second

Why simulate lateness? In the real world, events are NEVER perfectly on time. A rider's phone might lose signal in a subway tunnel for 8 seconds. The payment system might batch-send transactions every 5 seconds. GPS updates might lag. This producer lets you see how your Flink pipeline handles these real-world situations.

Flink in Production

Do you actually need streaming? In 10 years as a data engineer, Zach Wilson (the workshop instructor) had literally two use cases that genuinely needed streaming:

  1. Netflix fraud detection — 5 minutes of delay = 5 more minutes of a hacked account
  2. Airbnb surge pricing — supply/demand changes rapidly and prices must update in real-time

Everything else was daily batch, or hourly/15-minute micro-batch. Before committing to streaming, ask: "Is something automated going to act on this data in real-time?" If a human is just looking at dashboards, micro-batch is simpler.

Spark Streaming vs Flink

Spark Streaming

Micro-batch (pull architecture). Processes data in small batches every 15-30 seconds. Like checking your mailbox every few minutes.

Good when: you already use Spark, latency of seconds is acceptable.

Flink

True streaming (push architecture). Events flow through continuously, one by one. Like having mail delivered to your desk instantly.

Good when: you need sub-second latency, complex windowing, or event-time processing.
